System overview

backend/src/index.ts · docker-compose.yml

One React single-page app talks to one Express API over HTTPS. That API is the single point of contact for both the browser and the switches — it terminates a TLS MQTT connection to a Mosquitto broker, and every switch on the network publishes to and subscribes from that same broker. Postgres holds all state; OpenSearch is provisioned alongside it but is not wired into anything yet (see Dormant pieces).

Backend: a monolith, not microservices

backend/src/controllers/*.ts (24 files) · backend/src/services/*.ts

Every piece of business logic — auth, device CRUD, VLAN, PoE, routing, port security, alarms, telemetry ingestion, topology — runs inside one Node process started by index.ts. There are no independently deployable services, no internal service-to-service API, no message queue between components. This is a reasonable, well-organized architecture for the project's size — it just isn't microservices, regardless of how the containers in docker-compose.yml are described.

Scaling constraint

The command/response correlation layer (commandWaiter.ts) is an in-process EventEmitter, and the topology poller is an in-process setInterval. Neither survives being split across replicas: if you ran two copies of this backend behind a load balancer, an HTTP request handled by replica A waiting on a switch's MQTT reply would never be notified if that reply happened to land on replica B's socket. Horizontal scaling isn't safe today without moving that correlation into shared state (Redis pub/sub, for example) first.

Device communication (MQTT)

backend/src/services/mqttService.ts · deviceCommand.ts · commandWaiter.ts

Switches and the platform speak over five topic types, all under a per-serial-number namespace parsed by topicParser.ts:

TopicDirectionPurpose
switch/<sn>/first_seenSwitch → PlatformZero-touch onboarding — auto-creates the Device row, unassigned until an admin claims it
switch/<sn>/telemetrySwitch → PlatformCPU/memory/temperature + per-interface byte/packet counters, ~every 5 min
switch/<sn>/eventSwitch → PlatformAsync notifications — port_up, port_down, etc.
switch/<sn>/statusSwitch → Platformonline/offline/rebooting — offline also arrives via MQTT LWT
switch/<sn>/responseSwitch → PlatformReply to a command, correlated by request_id
switch/<sn>/requestPlatform → SwitchConfig/exec command, published by every feature controller

Request/response over pub-sub

MQTT has no native request/response — the platform builds one on top. Every command gets a generated request_id (req_<12 hex>), is logged to CommandLog before it's sent, and — when the caller needs to know the outcome before answering its own HTTP request — the handler blocks on a Promise that only resolves when a matching response lands, or after a 15s timeout.

  M->>S: forwarded by broker
  S-->>M: switch/<sn>/response { request_id, status }
  M->>API: responseHandler updates CommandLog
  API->>W: notifyResponse(request_id, data)
  W-->>API: Promise resolves
  API-->>U: 200 confirmed / 422 rejected by switch
Confirm-then-persist

Nothing is written to the database as "applied" until the switch's own response says status: 0. A rejected command is reported back with the switch's own message — the platform never assumes a config change succeeded.

Multi-vendor command layer

backend/src/commands/ — 16 feature modules

Every switch-facing feature (VLAN, PoE, port security, STP, DHCP, routing, link aggregation, loop detection, system, topology…) is split into a types.ts (the method contract), one file per switch family (ac5.ts, tr.ts), and an index.ts barrel. registry.ts is the only place that maps a Device.model string to a concrete set of builders — controllers never branch on model name directly, they call getDeviceCommands(model) / getDeviceCapabilities(model) and the right vendor's CLI strings come back. 

// controllers never see a vendor string — only this:
const commands = getDeviceCommands(device.model);
if (!commands.portSecurity.bindStaticMac) return 400; // not supported on this model
await runDeviceCommand(device, commands.portSecurity.bindStaticMac(target, mac, sticky));

Adding a third switch family means adding new files under commands/ — zero controller changes. CLI strings in this layer are only ever written after being confirmed against a real terminal ? session, never guessed.

Most per-feature config (PoE, STP, loop detection, port security) is columns directly on Port rather than separate tables — a pragmatic choice that keeps per-port reads to one query, at the cost of a wide table.

Authentication & RBAC

backend/src/middlewares/authMiddleware.ts

JWT access + refresh tokens (bcrypt-hashed passwords, cost 10), accepted either as an accessToken cookie or a Bearer header. verifyUser decodes the token, loads the user fresh from Postgres on every request (not just trusting the JWT payload), and attaches it to req.user. requireRole(...roles) gates individual routes.

RoleDevice visibility
SUPERADMINEvery device, unrestricted
ADMINDevices in their own organization only
USERDevices explicitly assigned to them only

The same three-tier scoping rule (deviceWhereForUser-style helper) is re-implemented locally in most controllers rather than imported from one shared module — consistent in behavior everywhere it's used, but duplicated rather than centralized.

Frontend

megh-frontend/src — React 19, Vite 7, React Router 7

A conventional page/component SPA: main.tsx defines the route tree, App.tsx is the authenticated shell (header + sidebar + outlet), and per-domain pages live under pages/ with feature-specific config panels under component/config/. Auth gating is a localStorage flag check, not client-side JWT validation — the API is the real gate.

  • Charts — Recharts (dashboard stat trends, port traffic)
  • Topology — @xyflow/react + dagre for auto-layout graph rendering
  • Export — xlsx / jspdf, dynamically imported so they don't bloat the main bundle until a user actually exports

The backend image's entrypoint runs migrations and seeds on every container start: 

npx prisma migrate deploy && npx prisma db seed && node dist/index.js

The seed script upserts a single admin@megh.com SUPERADMIN (password hashed at seed time) and is a no-op on repeat runs — it won't overwrite an existing password.

Dormant & unverified pieces

Honest findings — provisioned but not load-bearing

Three things exist in the repo or the deploy config but have no live call path today:

OpenSearch

A full service is provisioned in docker-compose.yml and a client is instantiated in db/openSearchClient.ts — but it is never imported anywhere else. Running, but doing nothing.

audit model

The audit Prisma model (action/performedBy/entity) exists but no controller ever writes to it — there's no audit trail today despite the schema being ready for one.

dashboardController.getAllSwitches

Still routed at /dashboard/get-all-switch-list, still serving hardcoded seed data (seed/data.ts's mockSwitches), unauthenticated. The real dashboard (Dashboard.tsx) doesn't call it — it's dead weight, not a security hole in practice, but worth removing.
